## 1. 프로젝트 개요

GameTrade는 게임 아이템 판매 정보를 등록하고 조회하는 소규모 웹 애플리케이션이다.

판매자는 게임, 서버, 아이템명, 가격, 수량, 설명을 등록한다. 다른 사용자는 목록과 검색으로 그 정보를 본다. 거래 상태는 판매자가 화면에서 바꾼다. 결제, 포인트, 정산, 구매자 지정, 실시간 채팅은 만들지 않는다.

참고 범위는 대한민국의 게임 아이템 거래 서비스가 다루는 정보(게임, 서버, 아이템, 가격, 판매 상태)까지다. 특정 서비스의 화면, 문구, 코드, 데이터 구조를 복제하지 않는다. 샘플 게임 이름도 가상 이름을 사용한다.

### 1.1 개발 목적

Laravel과 MySQL로 요청 처리, 폼 검증, 세션 인증, Eloquent, 권한 검사, REST API, 기본 보안을 한 프로젝트에서 보여 주는 포트폴리오다. 화면은 Blade이고, 같은 규칙은 `/api/v1`에서도 동작한다.

### 1.2 개발 환경

| 항목 | 선택 |
| --- | --- |
| 운영체제 | macOS |
| IDE | Cursor |
| 언어 | PHP (XAMPP에 포함된 버전, 8.1 이상을 전제) |
| 데이터베이스 | XAMPP의 MariaDB. SQL은 MySQL 8과 MariaDB 10.4 이상에서 동작하는 범위로 작성 |
| 웹 서버 | Apache |
| 로컬 환경 | XAMPP |
| 프론트엔드 | HTML, CSS. 핵심 기능은 JavaScript 없이 동작 |
| DB 접근 | PDO |
| 버전 관리 | Git |

PHP 버전은 구현 1단계에서 `php -v`로 확인하고, 8.1 미만이면 그 사실을 README에 적는다. `password_hash()`, `password_verify()`는 이 범위에서 사용한다.

### 1.3 사용자 역할

역할 테이블은 두지 않는다. 관리자 화면은 범위 밖이다.

| 역할 | 설명 | 할 수 있는 일 |
| --- | --- | --- |
| 방문자 | 로그인하지 않은 브라우저 | 목록 조회, 상세 조회, 검색, 게임 필터, 회원가입, 로그인 |
| 회원 | 로그인에 성공한 사용자 | 방문자 기능, 자기 상품 등록, 자기 상품의 수정·삭제·상태 변경, 내 판매 상품 조회 |

구매자 역할은 없다. 다른 회원의 상품을 구매하거나 상태를 바꾸는 기능은 없다. 거래 진행과 완료는 판매자가 자신의 상품에 표시하는 상태다.

한 사용자는 여러 상품을 등록할 수 있다. 한 상품의 판매자는 한 명이다.

## 2. 범위

### 2.1 이번 프로젝트에 포함

- 회원가입, 로그인, 로그아웃, 세션 유지
- 비밀번호는 `password_hash()` 결과만 저장
- 아이템 목록, 상세, 아이템명 검색, 게임별 필터
- 로그인 회원의 아이템 등록, 본인 상품 수정·삭제
- 판매 중, 거래 진행 중, 거래 완료 상태와 허용된 전환
- 서버 측 입력 검증과 작성자 권한 검사
- 보안 요구사항(`docs/security-and-testing.md`)
- 로그인한 사용자의 내 판매 상품 목록. 페이지네이션과 정렬 선택은 포함하지 않는다
- P1으로 분류된 정렬, 페이지네이션, 기본 반응형 레이아웃

### 2.2 이번 프로젝트에서 제외 (P2)

- 실제 결제, 포인트 충전, 정산, 외부 결제 API
- 실시간 채팅
- 복잡한 관리자 페이지
- 이미지 업로드
- 이메일 인증, 비밀번호 찾기, 소셜 로그인
- 구매자 지정, 쪽지, 알림, 찜, 신고
- 상품 이미지, 다중 이미지, 파일 첨부
- 회원 탈퇴, 프로필 수정, 비밀번호 변경
- 낙관적 잠금, 전문 검색 엔진, 캐시, 큐

제외 항목은 화면 문구나 README에서 구현된 기능처럼 적지 않는다.

## 3. 기능 요구사항

### 3.1 회원

#### F-AUTH-01 회원가입

사용자는 아이디와 비밀번호로 가입한다. 이메일, 닉네임, 전화번호는 받지 않는다.

입력:

| 필드 | 규칙 |
| --- | --- |
| 아이디 | 필수. 4자 이상 20자 이하. 영문, 숫자, 밑줄(`_`)만 허용. 앞뒤 공백은 제거한 뒤 검사. 대소문자는 구분한다 |
| 비밀번호 | 필수. 8자 이상 64자 이하. 조합 규칙(영문+숫자 등)은 두지 않는다 |
| 비밀번호 확인 | 필수. 비밀번호와 같아야 한다 |

처리 규칙:

- 가입 전에 형식을 검사한다.
- 같은 아이디가 있으면 가입시키지 않고, "이미 사용 중인 아이디입니다."를 보여 준다.
- 동시 가입은 DB의 UNIQUE 제약이 최종 판단이다. 중복 키 오류도 같은 메시지로 바꾼다.
- 비밀번호는 `password_hash($password, PASSWORD_DEFAULT)` 결과만 `users.password_hash`에 저장한다.
- 가입 성공 시 로그인 처리 함수로 세션을 만들고 목록으로 이동한다. 플래시 메시지는 "가입했습니다."다. 세션 ID 재발급은 로그인 함수 안에서만 한다.

완료 조건:

- 규칙을 만족하는 신규 아이디로 가입하면 `users`에 행이 생긴다.
- DB에 입력한 비밀번호 문자열이 그대로 없어야 한다.
- 형식 오류나 중복 아이디면 행이 생기지 않고, 폼에 아이디가 다시 채워진다. 비밀번호는 다시 채우지 않는다.
- 가입에 성공하면 목록 헤더에 그 아이디가 보인다.

#### F-AUTH-02 로그인

입력은 아이디와 비밀번호다.

- 아이디가 없거나 비밀번호가 틀리면 둘 다 같은 메시지 "아이디 또는 비밀번호가 올바르지 않습니다."를 보여 준다.
- 성공하면 세션에 사용자 `id`와 `username`을 저장하고, 세션 ID를 새로 발급한다.
- 이미 로그인한 사용자가 로그인 화면에 오면 목록으로 보낸다.

#### F-AUTH-03 로그아웃

- 로그아웃은 POST로만 처리한다.
- 세션 데이터를 비우고 세션을 폐기한 뒤 목록으로 이동한다.
- CSRF 토큰이 없으면 로그아웃하지 않는다.

#### F-AUTH-04 로그인 상태 유지

기본 해석은 "사이트를 이동하는 동안 다시 로그인하지 않아도 된다"이다. PHP 세션 쿠키를 사용하고, 브라우저를 닫으면 끝나는 세션으로 둔다. 자동 로그인(remember me)과 장기 쿠키는 만들지 않는다. 해석이 다를 수 있으므로 Q6에 남긴다.

헤더는 세션이 있으면 아이디, 아이템 등록, 로그아웃을 보여 준다. 세션이 없으면 로그인, 회원가입을 보여 준다.

### 3.2 게임 아이템 조회

#### F-ITEM-01 전체 목록

`GET /index.php`는 등록된 상품을 보여 준다. 판매 중만이 아니라 거래 진행 중, 거래 완료도 포함한다. 상태 필터는 요구사항에 없으므로 만들지 않는다.

각 행에 보일 항목:

- 게임명
- 서버명
- 아이템명 (상세 페이지 링크)
- 판매 가격 (천 단위 구분, 뒤에 `원`)
- 판매 수량
- 판매 상태 (한글 라벨)
- 등록 일시 (`Y-m-d H:i`)

P0의 정렬은 `created_at DESC, id DESC`로 고정한다. 사용자가 고르는 정렬 UI는 F-ITEM-10(P1)이다. 충돌 C1을 본다.

결과가 없으면 "등록된 아이템이 없습니다."를 보여 준다.

#### F-ITEM-02 상세 조회

`GET /item.php?id={id}`는 목록 항목에 더해 다음을 보여 준다.

- 아이템 설명 (없으면 "설명이 없습니다.")
- 판매자 아이디
- 수정 일시

존재하지 않거나 정수가 아닌 `id`는 "상품을 찾을 수 없습니다."와 HTTP 404다.

로그인한 작성자에게만 수정, 삭제, 상태 변경 폼을 보여 준다. 다른 회원과 방문자에게는 그 폼을 출력하지 않는다. 폼을 숨기는 것은 편의를 위한 것이고, 권한 판단은 서버가 POST에서 다시 한다.

#### F-ITEM-03 게임별 분류

목록의 게임 선택 값으로 해당 게임의 상품만 조회한다. 선택값은 `games.id`다. 서버명과 게임명은 상품 행에 항상 표시한다.

존재하지 않는 `game_id`는 빈 결과와 "검색 결과가 없습니다."로 처리한다. SQL 오류로 보여 주지 않는다.

#### F-ITEM-04 아이템명 검색

목록의 검색어로 아이템명을 부분 일치 검색한다. 대소문자는 데이터베이스 기본 콜레이션을 따른다.

- 앞뒤 공백은 제거한다.
- 공백만 있으면 검색 조건 없이 목록을 보여 준다.
- 100자를 넘는 검색어는 100자까지만 사용하거나 검증 오류로 거절한다. 기본안은 100자 초과를 검증 오류로 거절한다.
- `%`와 `_`는 LIKE 패턴에서 제거하거나 이스케이프한다. 기본안은 제거다.
- 비교는 SQL `LIKE`와 바인딩 파라미터로 한다.

검색 결과가 없으면 "검색 결과가 없습니다."를 보여 준다. 게임 필터와 검색은 함께 쓸 수 있다. 둘 다 AND 조건이다.

#### F-ITEM-05 가격과 상태 표시

가격은 0보다 큰 정수 원이다. 목록과 상세에 상태 한글명을 표시한다.

| DB 값 | 화면 라벨 |
| --- | --- |
| `ON_SALE` | 판매 중 |
| `IN_PROGRESS` | 거래 진행 중 |
| `COMPLETED` | 거래 완료 |

#### F-ITEM-10 정렬 (P1)

목록에서 다음 중 하나를 고른다. 기본값은 최신순이다.

| 요청 값 | SQL |
| --- | --- |
| `latest` | `created_at DESC, id DESC` |
| `price_asc` | `price ASC, id DESC` |
| `price_desc` | `price DESC, id DESC` |

허용 목록에 없는 값은 `latest`로 처리하거나 검증 오류로 거절한다. 기본안은 `latest`로 되돌린다. 컬럼 이름을 요청 값 그대로 SQL에 붙이지 않는다.

#### F-ITEM-11 페이지네이션 (P1)

한 페이지 10건이다. `page`는 1 이상의 정수다. 없거나 1보다 작거나 정수가 아니면 1페이지로 본다. 마지막 페이지를 넘는 값은 빈 목록과 페이지 이동을 보여 준다.

P0에서는 페이지네이션 없이 조건에 맞는 행을 모두 보여 준다. 샘플 데이터 규모를 작게 유지한다.

### 3.3 아이템 판매 등록

#### F-ITEM-06 등록

로그인한 사용자만 `GET /item-create.php` 폼을 열고 `POST /item-create.php`로 저장한다.

| 입력 | 저장 위치 | 규칙 |
| --- | --- | --- |
| 게임 / 서버 | `items.server_id` | 필수. 존재하는 `game_servers.id`. 화면에는 게임명과 서버명이 함께 보여야 한다. 기본 UI는 C3의 선택지 A를 따른다 |
| 아이템명 | `items.item_name` | 필수. 앞뒤 공백 제거 후 1자 이상 100자 이하 |
| 판매 가격 | `items.price` | 필수. 정수. 1 이상 100,000,000 이하. 소수, 음수, 0, 쉼표 포함 문자열은 거절 |
| 판매 수량 | `items.quantity` | 필수. 정수. 1 이상 9,999 이하 |
| 아이템 설명 | `items.description` | 기본안은 선택. 공백이면 NULL. 2,000자 이하. Q7 |

등록 시 상태 입력은 받지 않는다. 항상 `ON_SALE`이다.

성공하면 그 상품의 상세 페이지로 이동한다. 실패하면 같은 폼에 오류를 보여 주고, 비밀번호가 아닌 입력값은 다시 채운다. 설명에 HTML을 넣어도 저장은 하되, 출력할 때 이스케이프한다.

비로그인 POST는 저장하지 않고 로그인 페이지로 보낸다. 로그인 후 원래 폼으로 자동 복귀하는 기능은 만들지 않는다.

같은 아이템명의 상품이 여러 개 있어도 된다. 아이템명 UNIQUE는 두지 않는다.

수량은 재고에서 빠지는 값이 아니다. 판매자가 적어 두는 판매 수량이며, 상태 변경 때 줄이지 않는다.

### 3.4 수정과 삭제

#### F-ITEM-07 수정

- 작성자만 `GET /item-edit.php?id={id}`와 `POST /item-edit.php`를 사용할 수 있다.
- 수정 가능한 필드는 등록 필드와 같다. 판매자(`user_id`)와 등록 일시는 바꾸지 못한다.
- 상태 변경은 이 폼에서 하지 않는다. F-ITEM-08에서 한다.
- 기본안: 내용 수정은 상태가 `ON_SALE`일 때만 된다. Q3.
- 다른 사용자와 비로그인 사용자는 수정할 수 없다.
- 성공하면 상세 페이지로 이동한다.

권한 실패와 부재의 구분:

- `id`가 없거나 상품이 없으면 404
- 상품은 있으나 로그인 사용자가 작성자가 아니면 403과 "이 상품을 수정할 수 없습니다."
- 작성자이지만 허용 상태가 아니면 403과 "현재 상태에서는 수정할 수 없습니다."
- 로그인하지 않았으면 로그인 페이지로 이동

#### F-ITEM-08 삭제

- 작성자만 삭제할 수 있다.
- `GET /item-delete.php?id={id}`는 확인 화면만 보여 준다. 이 요청으로 DELETE를 실행하지 않는다.
- `POST /item-delete.php`만 행을 삭제한다.
- 기본안: `ON_SALE`일 때만 삭제한다. Q3.
- 성공하면 목록으로 이동하고 "상품을 삭제했습니다."를 보여 준다.
- 물리 삭제다. 삭제 이력 테이블은 두지 않는다.
- 권한과 부재의 구분은 수정과 같다. 메시지는 "삭제"로 바꾼다.

### 3.5 거래 상태

#### F-ITEM-09 상태 변경

상태 값은 다음 세 가지를 기본안으로 한다.

| 상태 | 의미 |
| --- | --- |
| `ON_SALE` | 판매 의사가 있는 등록 상태. 등록 직후 값 |
| `IN_PROGRESS` | 판매자가 거래를 진행 중으로 표시한 상태. 거래 상대 컬럼은 없다 |
| `COMPLETED` | 판매자가 거래를 마쳤다고 표시한 상태. 여기서 다른 상태로 돌아가지 않는다 |

허용 전환은 판매자만 할 수 있다.

| 현재 | 허용되는 다음 상태 |
| --- | --- |
| `ON_SALE` | `IN_PROGRESS` |
| `IN_PROGRESS` | `COMPLETED`, `ON_SALE` |
| `COMPLETED` | 없음 |

`IN_PROGRESS`에서 `ON_SALE`로 되돌리는 것은 진행 표시를 취소하는 동작이다. 금전 환불이나 상대방 알림은 없다.

거절하는 요청의 예:

- `ON_SALE`에서 `COMPLETED`로 바로 변경
- `COMPLETED`에서 어떤 상태로도 변경
- 현재 상태와 같은 값으로 다시 저장
- 정의되지 않은 문자열
- 다른 사용자 또는 비로그인 요청

상세 화면의 상태 폼에는 현재 상태에서 갈 수 있는 다음 상태만 선택지로 나온다. `COMPLETED`인 작성자에게는 상태 폼을 보여 주지 않는다.

성공하면 상세 페이지로 돌아온다. SQL은 현재 상태를 WHERE에 넣어, 그 사이에 상태가 바뀌었으면 갱신하지 않고 "상태가 이미 변경되었습니다."를 보여 준다.

거래 취소 상태를 추가할지는 Q2다. 기본 스키마에는 넣지 않는다.

### 3.6 내 판매 상품

#### F-ITEM-12 내 판매 상품

로그인한 사용자가 `GET /my-items.php`에서 자신의 상품만 본다.

- 조건은 `items.user_id = 세션 사용자 id`
- 정렬은 `created_at DESC, id DESC`
- 각 행에서 상세, 수정, 삭제로 이동할 수 있다
- 수정·삭제 가능 여부는 상태 규칙을 따른다. 불가능한 상태면 링크 대신 상세만 보여 준다
- 비로그인 접근은 로그인 페이지로 보낸다
- 결과가 없으면 "등록한 상품이 없습니다."
- 페이지네이션과 정렬 선택은 넣지 않는다. 정렬은 최신순 고정이다

이 기능은 P0다.

## 4. 비기능 요구사항

- 화면 문구는 한국어로 작성한다.
- 문자 집합은 UTF-8, DB는 `utf8mb4`다.
- 데이터 변경은 POST와 CSRF 검사 후에만 한다.
- SQL 값은 PDO prepared statement로 바인딩한다.
- HTML로 출력하는 모든 동적 문자열은 이스케이프한다.
- 사용자에게 DB 오류 문구, 스택 트레이스, 파일 경로, SQL을 보여 주지 않는다.
- 접속 정보는 웹 문서 루트 밖의 설정 파일에 둔다.
- 핵심 흐름은 서버가 HTML을 렌더링한다. 목록, 등록, 수정, 삭제, 로그인에 JavaScript를 필수로 두지 않는다.
- 동시 수정 잠금은 두지 않는다. 한 상품을 고칠 수 있는 사람은 판매자 한 명이고, 상태 변경 SQL이 현재 상태를 조건으로 사용한다.

## 6. 확정된 결정

2026-10-15에 구현 기준을 확정했다. 정렬 UI와 페이지네이션, 반응형 레이아웃은 계속 P1이다.

### C1. 정렬은 요구 기능이면서 P1이다

- 조회 요구사항은 최신순과 가격순 정렬을 포함한다.
- 우선순위 절은 두 정렬을 P1로 둔다.

문제: P0만 끝내면 사용자가 정렬을 고를 수 없다.

기본안:

- P0 쿼리는 `ORDER BY created_at DESC, id DESC`를 항상 사용한다.
- 정렬 선택 UI와 `price_asc`, `price_desc`는 P1이다.
- P0도 정렬 자체는 SQL ORDER BY로 수행한다.

### C2. 내 판매 상품은 본문 요구사항이면서 P1이다

- 회원 상품 조회, 상태 확인, 상세 이동, 수정·삭제는 요구사항에 있다.
- 우선순위 절은 내 판매 상품 목록을 P1로 둔다.
- 수정과 삭제는 P0다.

문제: P0에 내 목록이 없으면 작성자는 공개 목록에서 자기 글을 찾거나 주소의 `id`를 알아야 수정·삭제에 들어갈 수 있다. 상세 페이지에는 작성자일 때 수정·삭제 버튼이 있다.

확정:

- 페이지네이션과 정렬 선택이 없는 내 판매 목록을 P0에 포함한다.
- 정렬은 `created_at DESC, id DESC`로 고정한다.

### C3. 게임명·서버명 입력과 별도 테이블

- 등록 입력 항목은 게임명과 서버명이다. 자유 입력으로 읽을 수 있다.
- 데이터베이스 검토 요청은 별도 테이블이 필요한지 판단하라고 한다.
- 게임별 필터는 P0다.
- 관리자 페이지는 P2라서, 사용자가 게임을 직접 추가하는 화면은 없다.

선택지 A (확정):

- `games`, `game_servers` 테이블을 두고 시드 데이터로 게임을 넣는다.
- 등록 화면은 서버를 `게임명 - 서버명`으로 고르는 `<select>`다. 저장값은 `server_id` 하나다. 게임은 서버의 부모로 결정된다.
- 필터는 `games.id`로 한다.
- 사용자는 시드에 없는 게임을 그 자리에서 추가할 수 없다. 게임을 늘릴 때는 시드 SQL을 수정한다.

선택지 B:

- `items.game_name`, `items.server_name` 문자열만 둔다.
- 화면은 두 개의 텍스트 입력이다.
- 테이블 수는 줄지만, "루멘"과 "루멘 "처럼 표기가 달라지면 게임 필터가 나뉜다.

테이블, ERD, 화면, 흐름은 선택지 A로 구현한다.

## 8. 완료의 정의 (P0)

다음이 모두 만족되면 P0가 끝난 것이다.

- 방문자가 목록, 상세, 게임 필터, 아이템명 검색을 사용할 수 있다.
- 회원이 가입하면 바로 로그인되고, 로그아웃 후 다시 로그인할 수 있다.
- 로그인한 사용자만 상품을 등록할 수 있고, 내 판매 목록에서 자신의 상품을 찾을 수 있다.
- 작성자만 자신의 `ON_SALE` 상품을 수정·삭제할 수 있다.
- 허용된 상태 전환만 저장된다.
- 보안 문서의 P0 테스트를 실행했고, 결과를 테스트 기록에 실제 결과로 적었다.
- 결제, 채팅, 이미지 업로드가 코드와 화면에 없다.
