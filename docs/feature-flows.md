# GameTrade 기능 동작 흐름

상태: Laravel 구현 기준  
기준일: 2026-10-15

화면 주소는 `routes/web.php`다. 데이터 변경이 성공하면 다른 주소로 리다이렉트한다. 성공 응답으로 폼 HTML을 다시 그리지 않는다.

공통 예외:

- DB 연결 실패와 예상하지 못한 예외는 `storage/logs/laravel.log`에만 남긴다. 화면은 "잠시 후 다시 시도해 주세요."다.
- 웹의 변경 요청에 CSRF 토큰 `_token`이 없거나 틀리면 HTTP 419이고, 데이터는 변하지 않는다. 작성자가 아니면 HTTP 403이다.
- 지원하지 않는 메서드는 405다. `GET /logout`은 405이고 `Allow: POST`다.

쿼리 형태는 `docs/database-design.md` 8절을 따른다.

## 1. 회원가입

사용자의 행동:

1. 헤더에서 회원가입을 연다.
2. 아이디, 비밀번호, 비밀번호 확인을 입력하고 제출한다.

HTTP 요청:

- 화면: `GET /register`
- 제출: `POST /register`
- 필드: `username`, `password`, `password_confirm`, `_token`

서버 처리:

1. Laravel이 세션을 연다.
2. 이미 로그인되어 있으면 목록으로 리다이렉트한다. `guest` 미들웨어다.
3. GET이면 빈 폼을 보여 준다.
4. POST면 CSRF를 검사한다.
5. `RegisterRequest`가 아이디를 trim하고 형식(4~20자, 영문·숫자·밑줄)을 검사한다.
6. 비밀번호 길이 8~64자와 확인 값 일치를 검사한다.
7. 오류가 있으면 DB를 호출하지 않고 폼을 다시 그린다. 아이디만 유지한다.
8. `User` 모델의 `hashed` 캐스트가 해시를 만든다.
9. `User::create()`가 INSERT를 실행한다.

데이터베이스:

```sql
INSERT INTO users (username, password)
VALUES (:username, :password);
```

`:password`는 해시 문자열이다.

처리 결과:

- 성공하면 로그인과 같은 처리로 세션을 만들고 플래시에 "가입했습니다."를 넣은 뒤 `GET /`로 이동한다.
- 중복 UNIQUE면 "이미 사용 중인 아이디입니다."를 폼에 보여 준다.

사용자에게 보이는 화면:

- 성공 후 목록. 헤더에 가입한 아이디와 성공 메시지
- 실패 시 회원가입 폼과 필드 오류

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 아이디 형식 오류 | 가입 행 없음. 형식 안내 |
| 비밀번호 불일치 또는 길이 오류 | 가입 행 없음 |
| 이미 있는 아이디 | 가입 행 없음. 중복 메시지 |
| 동시에 같은 아이디 INSERT | 한 건만 저장. 나머지는 중복 메시지 |
| CSRF 누락 | 419. 행 없음 |
| 로그인 상태에서 POST | 목록으로 이동. 행 없음 |

## 2. 로그인

사용자의 행동:

1. 로그인 화면에서 아이디와 비밀번호를 입력하고 제출한다.

HTTP 요청:

- 화면: `GET /login`
- 제출: `POST /login`
- 필드: `username`, `password`, `_token`

서버 처리:

1. 이미 로그인되어 있으면 목록으로 보낸다.
2. POST CSRF를 검사한다.
3. `Authenticator`가 아이디로 회원을 찾는다.
4. 회원이 없어도 더미 해시와 한 번 비교한다. 계정 존재 여부에 따라 응답 시간 차이가 크게 벌어지지 않게 하기 위한 절차다.
5. 회원이 있고 입력 비밀번호가 `users.password` 해시와 맞으면 성공이다.
6. 성공 시 세션 ID를 재발급하고 세션에 사용자 id와 username만 저장한다.

데이터베이스:

```sql
SELECT id, username, password
FROM users
WHERE username = :username;
```

실패해도 UPDATE는 없다. 로그인 실패 횟수 컬럼은 두지 않는다.

처리 결과:

- 성공: `GET /`로 이동
- 실패: 로그인 폼에 "아이디 또는 비밀번호가 올바르지 않습니다."

사용자에게 보이는 화면:

- 성공 후 목록. 헤더에 아이디와 로그아웃
- 실패 시 로그인 폼. 아이디는 다시 채우고 비밀번호는 비움

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 없는 아이디 | 공통 실패 메시지. 아이디가 없다는 문구는 쓰지 않음 |
| 비밀번호 불일치 | 같은 공통 실패 메시지 |
| 빈 값 | 같은 공통 실패 메시지 |
| CSRF 누락 | 419. 세션에 사용자 없음 |
| 세션 저장 경로를 쓸 수 없음 | 일반 오류 메시지. 로그에 원인 |

## 3. 로그아웃

사용자의 행동:

1. 헤더의 로그아웃 버튼을 누른다.

HTTP 요청:

- `POST /logout`
- 필드: `_token`

서버 처리:

1. GET이면 405로 종료한다. 세션은 유지한다.
2. CSRF를 검사한다.
3. `AuthController`가 세션을 폐기하고 목록으로 보낸다.

데이터베이스:

- 조회와 변경이 없다.

처리 결과:

- `GET /`로 이동한다.
- 이후 요청의 헤더는 로그인, 회원가입을 보여 준다.

사용자에게 보이는 화면:

- 목록. 별도 로그아웃 완료 페이지는 없다.

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| GET으로 로그아웃 주소 접속 | 405. 로그인 유지 |
| CSRF 누락 | 419. 로그인 유지 |
| 이미 로그아웃된 세션 | 목록으로 이동 |

## 4. 아이템 목록 조회

사용자의 행동:

1. 사이트를 열거나 로고를 누른다.

HTTP 요청:

- `GET /`

서버 처리:

1. 세션으로 헤더의 로그인 상태만 판단한다. 목록 자체는 로그인과 무관하다.
2. `ItemController::index`가 `Item` 목록 조건을 필터 없이 호출한다.
3. 각 행의 상태 코드를 `ItemStatus` 한글 라벨로 바꿔 표에 출력한다.
4. 텍스트는 Blade `{{ }}`로 이스케이프한다.

데이터베이스:

- `docs/database-design.md` 8.1의 목록 쿼리
- P0 ORDER BY는 `created_at DESC, id DESC`
- 게임 조건과 검색 조건은 붙이지 않는다

처리 결과:

- HTTP 200과 목록 HTML
- 0건이면 표 대신 "등록된 아이템이 없습니다."

사용자에게 보이는 화면:

- 게임, 서버, 아이템명, 가격, 수량, 상태, 등록일
- 아이템명 링크

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 쿼리 실패 | 일반 오류. 빈 표와 SQL 문구를 같이 보여 주지 않음 |
| 로그인 만료 | 목록은 그대로 보이고 헤더만 비로그인 상태 |

## 5. 아이템 검색

사용자의 행동:

1. 목록에서 게임을 고르거나 아이템명을 입력하고 검색한다.
2. 게임만, 이름만, 둘 다 조합할 수 있다.

HTTP 요청:

- `GET /?game_id={id}&q={단어}`
- 검색은 GET이다. 데이터를 바꾸지 않는다.
- CSRF는 요구하지 않는다.

서버 처리:

1. `game_id`가 없으면 게임 조건을 붙이지 않는다.
2. `game_id`가 있으면 정수인지 확인한다. 정수가 아니면 게임 조건을 무시하고 목록을 보여 준다.
3. `q`를 trim한다. 빈 문자열이면 이름 조건을 붙이지 않는다.
4. 100자를 넘으면 "검색어는 100자 이하로 입력해 주세요."를 보여 주고 쿼리하지 않는다. 이 경우에도 페이지 레이아웃은 목록 화면이다.
5. `%`와 `_`를 제거한다.
6. 남은 검색어가 있으면 `LIKE` 값의 양쪽에 `%`를 붙여 바인딩한다.
7. 게임과 이름은 AND다.
8. `sort`는 `latest`, `price_asc`, `price_desc`만 받는다. 없거나 그 밖이면 `latest`다. 컬럼 이름은 요청 값으로 만들지 않는다.
9. `page`는 1 이상의 정수만 받는다. 없거나 그 밖이면 1페이지다. 한 페이지는 10건이다. 마지막 페이지를 넘으면 목록은 비고 페이지 이동은 남긴다. 검색, 게임, 정렬은 페이지 링크에 유지한다.

데이터베이스:

- 8.1 목록 쿼리에 필요한 WHERE만 추가
- `game_id`는 정수 바인딩
- 이름 패턴은 문자열 바인딩
- 정렬 컬럼은 요청 문자열을 연결하지 않는다

처리 결과:

- 조건에 맞는 행만 200으로 표시
- 0건이면 "검색 결과가 없습니다."
- 선택한 게임과 검색어는 폼에 다시 표시한다

사용자에게 보이는 화면:

- 목록과 같은 표
- 검색 폼에 방금 입력한 값

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 없는 `game_id` | 빈 결과 메시지. SQL 오류 아님 |
| `q`에 `' OR 1=1 --` | 그 문자열을 이름 패턴으로만 바인딩. 전체 행이 나오지 않음. 따옴표가 이름에 들어간 상품만 부분 일치 |
| `q`가 `%`만 | 와일드카드를 제거하면 빈 검색어. 이름 조건 없이 목록 표시 |
| 검색어 101자 이상 | 검증 메시지. 쿼리 없음 |

가격순·최신순 UI는 P1이다. P1 요청 `sort=price_asc|price_desc|latest`일 때만 ORDER BY 상수 중 하나를 고른다. 그 외 값은 `latest`다.

## 6. 아이템 등록

사용자의 행동:

1. 로그인한 뒤 아이템 등록을 연다.
2. 서버, 아이템명, 가격, 수량, 설명을 입력하고 등록한다.

HTTP 요청:

- 화면: `GET /items/create`
- 제출: `POST /items`
- 필드: `server_id`, `item_name`, `price`, `quantity`, `description`, `_token`

서버 처리:

1. `auth` 미들웨어. 비로그인이면 `GET /login`으로 이동한다. GET과 POST 모두 적용한다.
2. GET이면 서버 목록을 읽어 폼을 보여 준다.
3. POST면 CSRF 후 `ItemRequest`가 값을 검사한다.
4. 가격과 수량은 정수 검증과 최소·최대 범위로 검사한다. `(int)` 캐스팅으로 큰 숫자를 자르지 않는다.
5. 설명은 trim 후 빈 값이면 null, 2,000자를 넘으면 오류다.
6. `server_id`가 `game_servers`에 있는지도 검증에서 확인한다.
7. 오류가 있으면 INSERT하지 않고 폼을 다시 그린다.
8. 성공하면 `ItemController::store`가 세션 사용자 id로 상품을 만든다. 상태는 항상 `ON_SALE`이다. 폼에 `status`가 있어도 무시한다.

데이터베이스:

- 서버 존재 SELECT
- `docs/database-design.md` 8.4 INSERT
- `user_id`는 세션

처리 결과:

- 성공: 새 id로 `GET /items/{id}` 이동. 플래시 "상품을 등록했습니다."
- 실패: HTTP 200 폼과 오류. 상태 코드 400을 쓰고 싶으면 400을 써도 된다. 기본안은 폼 재표시에 200을 사용한다.

사용자에게 보이는 화면:

- 성공 후 상세. 상태 라벨은 판매 중
- 실패 시 입력값을 유지한 등록 폼. 설명의 HTML은 입력란의 값으로만 보이고, 그 페이지에서 실행되지 않는다

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 비로그인 GET 또는 POST | 로그인으로 이동. INSERT 없음 |
| 필수값 누락, 가격 음수·0·소수, 수량 0 이하 | 폼 오류. INSERT 없음 |
| 없는 `server_id`를 조작해 POST | 서버 검증 오류. INSERT 없음 |
| 설명에 `<script>` 포함 | 저장은 된다. 상세 출력은 이스케이프되어 스크립트가 실행되지 않음 |
| CSRF 누락 | 419. INSERT 없음 |
| CHECK 제약을 통과한 검증 버그로 DB가 거절 | 일반 오류. 제약 문구는 화면에 없음 |

## 7. 아이템 수정

사용자의 행동:

1. 자기 상품 상세에서 수정을 연다.
2. 값을 바꾸고 저장한다.

HTTP 요청:

- 화면: `GET /items/{id}/edit`
- 제출: `PUT /items/{id}`
- 필드: `server_id`, `item_name`, `price`, `quantity`, `description`, `_token`, `_method=PUT`

서버 처리:

1. `auth` 미들웨어.
2. `id`가 숫자가 아니거나 상품이 없으면 404.
3. `ItemPolicy`가 작성자가 아니면 403 "이 상품을 수정할 수 없습니다."
4. 상태가 `ON_SALE`이 아니면 403 "현재 상태에서는 수정할 수 없습니다."
5. GET이면 기존 값을 폼에 넣는다. 출력은 이스케이프한다.
6. PUT이면 CSRF와 `ItemRequest`를 수행한다.
7. 검증을 통과하면 `Item::revise()`를 호출한다.
8. 폼의 `user_id`는 읽지 않는다. 경로의 상품 id로만 판단한다.

데이터베이스:

- 상세 SELECT
- 8.5 UPDATE. WHERE에 `id`, `user_id`, `status = 'ON_SALE'`

처리 결과:

- 성공: 상세로 이동. "상품을 수정했습니다."
- 값이 그대로여도 작성자가 판매 중이면 성공으로 본다. `UPDATE`가 0건이어도 다시 읽어 소유자와 상태가 같으면 성공이다.
- 그 사이에 상태가 바뀌었으면 "현재 상태에서는 수정할 수 없습니다."
- 검증 실패: 수정 폼 재표시

사용자에게 보이는 화면:

- 작성자의 판매 중 상품: 값이 채워진 수정 폼
- 성공 후 상세의 갱신된 값과 수정 시각

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 비로그인 | 로그인으로 이동. UPDATE 없음 |
| 없는 id | 404. UPDATE 없음 |
| 다른 회원의 상품 | 403. UPDATE 없음 |
| `IN_PROGRESS` 또는 `COMPLETED` | 403. UPDATE 없음 |
| 가격·수량·이름 오류 | 폼 오류. UPDATE 없음 |
| GET 쿼리스트링만으로 접근 | 폼만 표시. 저장되지 않음 |
| CSRF 누락 | 419 |

## 8. 아이템 삭제

사용자의 행동:

1. 자기 상품 상세에서 삭제를 연다.
2. 확인 화면에서 삭제 버튼을 누른다.

HTTP 요청:

- 확인: `GET /items/{id}/delete`
- 실행: `DELETE /items/{id}`
- 필드: `_token`, `_method=DELETE`

서버 처리:

1. `auth` 미들웨어.
2. 상품이 없으면 404.
3. 작성자가 아니면 403 "이 상품을 삭제할 수 없습니다."
4. `ON_SALE`이 아니면 403 "현재 상태에서는 삭제할 수 없습니다."
5. GET이면 아이템명과 경고 문장만 보여 준다. DELETE를 실행하지 않는다.
6. DELETE면 CSRF 후 `Item::removeListing()`을 호출한다.

데이터베이스:

```sql
DELETE FROM items
WHERE id = :id
  AND user_id = :user_id
  AND status = 'ON_SALE';
```

처리 결과:

- 성공: 목록으로 이동. "상품을 삭제했습니다."
- 0건 삭제는 수정과 같이 상태 변경 메시지로 처리한다.

사용자에게 보이는 화면:

- 확인 화면에 게임, 서버, 아이템명, 가격
- 성공 후 목록에서 그 행이 사라짐

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 비로그인 | 로그인으로 이동 |
| 다른 회원의 상품 GET 또는 POST | 403. 행 유지 |
| 상세 링크를 주소창에 넣어 GET | 확인 화면까지만. 행 유지 |
| POST CSRF 누락 | 419. 행 유지 |
| `COMPLETED` 상품 | 403. 행 유지 |

## 9. 거래 상태 변경

사용자의 행동:

1. 자기 상품 상세에서 가능한 다음 상태를 고르고 변경한다.

HTTP 요청:

- 폼 표시: `GET /items/{id}` 안의 폼
- 제출: `POST /items/{id}/status`
- 필드: `status`, `_token`
- `GET /items/{id}/status`는 라우트가 없다

서버 처리:

1. `auth` 미들웨어.
2. CSRF를 검사한다.
3. 상품이 없으면 404.
4. 작성자가 아니면 403 "이 상품의 상태를 변경할 수 없습니다."
5. `ItemStatus` 허용 표에 요청 `status`가 없으면 400 "허용되지 않는 상태 변경입니다." 행은 유지한다.
6. 있으면 `Item::transitionTo()`를 트랜잭션과 행 잠금 안에서 호출한다.
7. 폼에 있는 현재 상태를 신뢰하지 않는다. DB에서 읽은 현재 상태만 사용한다.

데이터베이스:

```sql
UPDATE items
SET status = :next_status
WHERE id = :id
  AND user_id = :user_id
  AND status = :current_status;
```

허용 쌍:

| 현재 | POST `status` |
| --- | --- |
| `ON_SALE` | `IN_PROGRESS` |
| `IN_PROGRESS` | `COMPLETED` 또는 `ON_SALE` |
| `COMPLETED` | 없음. 상세에 폼을 출력하지 않음 |

처리 결과:

- 허용된 전환이면 상세로 이동. "거래 상태를 변경했습니다."
- 그 사이에 상태가 바뀌어 허용 표에 없으면 400 "허용되지 않는 상태 변경입니다." 행은 유지한다.

사용자에게 보이는 화면:

- 판매 중 상품의 작성자: 선택지에 "거래 진행 중"만
- 거래 진행 중: "거래 완료", "판매 중"
- 거래 완료: 상태 문구만
- 다른 사용자와 방문자: 상태 문구만

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| `ON_SALE`에서 `COMPLETED`로 POST | 400. 상태 유지 |
| `COMPLETED`에서 POST | 400. 상태 유지 |
| 정의되지 않은 문자열 | 400. 상태 유지 |
| 다른 회원이 작성자인 상품 | 403. 상태 유지 |
| 비로그인 | 로그인으로 이동. 상태 유지 |
| 새로고침으로 POST 재전송 | 이미 바뀐 상태라 허용 표에서 400으로 거절된다 |

## 10. 내 판매 상품 조회

이 흐름은 P0다. 페이지네이션과 정렬 선택은 없다.

사용자의 행동:

1. 로그인한 뒤 헤더의 내 판매 상품을 연다.
2. 행에서 상세로 이동하거나, 판매 중이면 수정·삭제로 이동한다.

HTTP 요청:

- `GET /my/items`

서버 처리:

1. `auth` 미들웨어.
2. `ItemController::mine`이 세션 사용자의 상품만 조회한다.
3. 상태가 `ON_SALE`인 행만 수정, 삭제 확인 링크를 출력한다.
4. 모든 행에 상세 링크를 출력한다.
5. 다른 사용자의 id를 쿼리스트링으로 받지 않는다. 세션 값만 WHERE에 넣는다.

데이터베이스:

- 8.3 쿼리. `:user_id`는 세션

처리 결과:

- 200과 자신의 상품만
- 0건이면 "등록한 상품이 없습니다."

사용자에게 보이는 화면:

- 게임, 서버, 아이템명, 가격, 수량, 상태, 등록일, 동작 링크

오류와 예외:

| 상황 | 결과 |
| --- | --- |
| 비로그인 | 로그인으로 이동 |
| `user_id`를 URL에 붙여 호출 | 그 값을 무시. 세션 사용자의 목록만 표시 |
| DB 오류 | 일반 오류 |

이 화면은 조회만 한다. 수정, 삭제, 상태 변경의 실행 흐름은 7~9절이다.
