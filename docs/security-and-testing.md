# GameTrade 보안 요구사항과 테스트 계획

상태: Laravel 구현 기준  
기준일: 2026-10-15

보안 항목은 기능을 모두 만든 뒤 한 번에 얹지 않는다. P0 구현에 이미 포함되어 있다. 테스트 표의 브라우저 시나리오는 실행 기록이 이 문서에 없으면 미실시다. PHPUnit 시나리오는 `tests/Feature`에 있다.

## 1. 보안 요구사항

### 1.1 SQL 인젝션

적용:

- 사용자 값이 들어가는 조건은 Eloquent 바인딩만 사용한다.
- 요청 문자열을 SQL에 이어 붙이지 않는다.
- 목록에 추가할 수 있는 조건은 코드에 적힌 게임 id 비교와 아이템명 `LIKE`뿐이다.
- `sort`는 `latest`, `price_asc`, `price_desc`를 코드의 ORDER BY 상수에 대응한다. 없는 값은 최신순이다.
- 테이블명, 컬럼명을 요청으로 받지 않는다.
- LIKE에 넣기 전에 `%`와 `_`를 제거한다.

완료 조건: 검색어, 로그인 아이디, 아이템명에 SQL 구문을 넣어도 쿼리 구조가 바뀌지 않고, 의도한 컬럼의 값으로만 비교된다.

### 1.2 비밀번호

적용:

- 가입 시 `User` 모델의 `hashed` 캐스트만 저장한다. 컬럼은 `users.password`다.
- 로그인은 `Authenticator`의 해시 비교만 사용한다.
- 해시 알고리즘 이름이나 cost를 직접 구현하지 않는다.
- 비밀번호 최대 길이는 64자다. bcrypt가 72바이트를 넘는 입력을 자르는 문제를 입력 단계에서 피한다.
- 실패 메시지는 아이디 존재 여부를 구분하지 않는다.
- 없는 아이디에도 더미 해시와 한 번 비교한다.
- 해시를 로그, 플래시, HTML, 세션에 넣지 않는다.
- 수정 폼과 목록 조회에 `password` 컬럼을 포함하지 않는다. 로그인 확인만 그 컬럼을 읽는다.

완료 조건: `users.password`가 `$2y$`로 시작하고, 가입할 때 입력한 비밀번호 문자열과 다르다.

### 1.3 XSS

적용:

- HTML 본문, 속성, 입력값 재표시는 Blade `{{ }}`가 이스케이프한다.
- 상태 라벨은 고정 한글 문자열만 출력한다. DB 상태를 라벨 없이 그대로 신뢰하지 않고, 허용 코드만 매핑한다.
- 설명을 HTML로 해석하는 기능은 없다. 마크다운이나 `nl2br` 전에 이스케이프가 먼저다. 줄바꿈이 필요하면 이스케이프한 뒤 개행만 `<br>`로 바꾼다.
- CSS, 스크립트 파일에 상품 설명을 넣지 않는다.
- 오류 메시지에 요청 원문을 넣을 때도 이스케이프한다.

완료 조건: 아이템명과 설명에 `<script>alert(1)</script>`를 저장한 뒤 목록과 상세에서 경고창이 뜨지 않고, 태그가 글자로 보인다.

### 1.4 서버 측 입력 검증

적용:

- 브라우저 `required`, `type="number"`, `maxlength`는 보조다. 같은 규칙을 Form Request에서 다시 검사한다.
- 가격과 수량은 정수 검증과 문서에 적힌 최소·최대로 검사한다. `(int)` 캐스팅으로 큰 수를 자르지 않는다.
- 아이디는 정규식 `^[A-Za-z0-9_]{4,20}$`다.
- 상품 문자열은 trim 후 길이를 검사한다.
- `server_id`는 정수가 아니거나 서버 테이블에 없으면 거절한다.
- 상태 값은 현재 상태에서 허용된 다음 값만 받는다.
- 검증 실패 시 INSERT와 UPDATE를 호출하지 않는다.
- DB CHECK는 마지막 안전장치다. 사용자 메시지는 Form Request 검증 문구를 사용한다.

완료 조건: 필수값 누락, 음수 가격, 수량 0, 범위 밖 가격이 저장되지 않는다.

### 1.5 세션 인증

적용:

- 로그인 성공 후에만 `user_id`를 세션에 넣는다.
- 로그인 성공 직후 세션 ID를 재발급한다.
- 쿠키는 `HttpOnly`, `SameSite=Lax`다.
- 로컬 HTTP이므로 `Secure` 플래그는 끄고, README 개발 환경에 "로컬 HTTP라 Secure 쿠키를 사용하지 않는다"고 적는다.
- 비밀번호 변경 기능이 없으므로 비밀번호 변경 시의 세션 폐기는 범위 밖이다.
- 인증이 필요한 라우트는 `auth` 미들웨어를 붙인다. 메뉴에서 링크를 빼는 것만으로 끝내지 않는다.

완료 조건: 로그인 전 등록 화면 주소로 접속하면 로그인으로 이동하고, 로그인 후 다른 페이지로 이동해도 헤더에 같은 아이디가 남는다.

### 1.6 로그아웃 시 세션

적용:

- POST에서만 처리한다. GET은 405다.
- 세션을 폐기한다.
- 로그아웃 후 브라우저 뒤로 가기를 하면 캐시된 HTML이 보일 수 있다. 그 화면의 변경 폼을 다시 보내면 CSRF와 로그인 검사가 거절한다.
- 캐시 금지를 모든 응답에 넣는 작업은 P0 필수로 두지 않는다. 인증 화면의 `Cache-Control: no-store`는 구현 여력이 있으면 로그인 이후 HTML에 붙인다. 필수는 서버가 변경 요청을 거절하는 것이다.

### 1.7 작성자 권한

적용:

- 수정, 삭제, 상태 변경은 세션 `user_id`와 `items.user_id`를 서버에서 비교한다.
- hidden 필드의 작성자 id는 받지 않는다.
- 내 목록의 사용자 id도 URL로 받지 않는다.
- 상품이 없으면 404, 있으면 작성자가 아닐 때 403이다.
- UPDATE와 DELETE의 WHERE에 `user_id`를 넣어 SELECT 이후의 변경도 막는다.
- 내용 수정과 삭제는 `status = 'ON_SALE'`을 WHERE에 포함한다. Q3 기본안이다.

완료 조건: 다른 회원의 상품 id로 수정·삭제·상태 POST를 보내도 행이 바뀌지 않는다.

### 1.8 CSRF

적용:

- 모든 상태 변경 요청에 세션 토큰 `_token`을 실어 보낸다. 대상은 가입, 로그인, 로그아웃, 등록, 수정, 삭제, 상태 변경이다.
- 비교와 토큰 생성은 Laravel CSRF 미들웨어가 한다.
- 실패하면 HTTP 419이고 DB를 변경하지 않는다.
- GET 목록과 GET 검색에는 토큰을 요구하지 않는다. 그 요청은 데이터를 바꾸지 않는다.

완료 조건: 토큰을 뺀 POST는 데이터가 변하지 않는다. 정상 폼의 POST는 동작한다.

### 1.9 GET으로 데이터를 바꾸지 않음

적용:

| 변경 | 허용 메서드 |
| --- | --- |
| 가입, 로그인, 로그아웃, 상태 변경 | POST |
| 등록 | POST |
| 수정 | PUT |
| 삭제 | DELETE |
| 목록, 검색, 상세, 폼 표시, 삭제 확인, 내 상품 | GET |

- `GET /logout`은 405다.
- `GET /items/{id}/delete`는 확인 화면만 렌더링한다.
- 링크와 `<img src>`로 실행되는 변경 URL을 만들지 않는다.

완료 조건: 삭제 확인 주소를 새 탭으로 열어도 행이 남는다.

### 1.10 오류 메시지

적용:

- 데이터베이스 예외 메시지를 화면에 출력하지 않는다.
- `APP_DEBUG`는 끈다.
- 로그 파일은 `storage/logs/laravel.log`다. 웹에서 직접 열리지 않는다.
- 사용자 문구는 "잠시 후 다시 시도해 주세요."로 통일한다.
- 검증 오류와 403, 404, 419는 그 상황의 한글 문장만 보여 준다. 파일 경로와 SQL을 붙이지 않는다.

완료 조건: 잘못된 DB 비밀번호로 접속을 유도했을 때 화면에 호스트, 계정, 스택 트레이스가 보이지 않는다. 이 확인은 로컬에서만 하고, 확인 뒤 설정을 되돌린다.

### 1.11 접속 정보

적용:

- 계정과 비밀번호는 `.env`에만 둔다.
- 이 파일은 Git에 커밋하지 않는다. 예시는 `.env.example`이다.
- 로컬 서버의 문서 루트는 `public/`이다. `php artisan serve`가 그 디렉터리를 연다.
- 로컬 MySQL 계정 `gametrade`는 마이그레이션을 실행하므로 이 데이터베이스에서 테이블을 만들 수 있다.
- `.env`의 비밀번호를 설계 문서에 다시 적지 않는다. 샘플 계정 안내는 README만 본다.

완료 조건: `.env`가 저장소에 없고, 브라우저로 `.env` URL을 열 수 없다.

## 2. 테스트 계획

실행 방법의 기본은 브라우저에서 폼을 조작하는 것이다. 데이터 확인은 DBeaver나 MySQL 클라이언트로 해당 행을 조회한다. 변경이 없어야 하는 테스트는 실행 전후 행 수와 컬럼 값이 같은지 본다.

같은 규칙의 자동 검사는 `php artisan test`다. 브라우저로 보지 않은 항목은 이 표에 통과라고 적지 않는다.

공통 사전 준비:

- 스키마와 시드가 적용되어 있다.
- 회원 A, 회원 B가 있다.
- A의 판매 중 상품, A의 거래 진행 중 상품, A의 거래 완료 상품, B의 판매 중 상품이 각각 1건 이상 있다.
- 브라우저 쿠키를 비우면 비로그인 상태가 된다.

### 2.1 P0 시나리오

#### T01 회원가입 성공

- 목적: 정상 가입과 해시 저장
- 사전 조건: `new_user_t01` 아이디가 없다
- 실행: 회원가입 폼에 규칙에 맞는 아이디와 비밀번호를 제출한다. `users`를 조회한다
- 예상 결과: 목록으로 이동하고 헤더에 새 아이디와 "가입했습니다."가 보인다. 행이 1건 생기고 `password`는 입력 비밀번호와 다르다

#### T02 중복 아이디

- 목적: UNIQUE와 사용자 메시지
- 사전 조건: 회원 A가 있다
- 실행: A의 아이디로 가입을 제출한다
- 예상 결과: "이미 사용 중인 아이디입니다." 행이 늘지 않는다

#### T03 잘못된 비밀번호 로그인

- 목적: 인증 실패 시 세션을 만들지 않음
- 사전 조건: 회원 A의 비밀번호를 알고 있다
- 실행: A의 아이디와 다른 비밀번호로 로그인한다
- 예상 결과: "아이디 또는 비밀번호가 올바르지 않습니다." 헤더는 비로그인이다

#### T04 없는 아이디 로그인

- 목적: 계정 존재 여부를 메시지에서 숨김
- 사전 조건: 없음
- 실행: 존재하지 않는 아이디로 로그인한다
- 예상 결과: T03과 같은 메시지. "없는 아이디"라는 문구가 없다

#### T05 로그인과 로그아웃

- 목적: 세션 유지와 폐기
- 사전 조건: 회원 A
- 실행: 로그인 후 목록과 상세를 연다. 로그아웃 후 등록 주소를 연다
- 예상 결과: 로그인 후 헤더에 A의 아이디. 페이지 이동 후에도 유지. 로그아웃 후 등록 주소는 로그인 화면으로 이동한다

#### T06 목록과 상세

- 목적: 공개 조회
- 사전 조건: 시드 상품
- 실행: 비로그인으로 목록과 상세를 연다
- 예상 결과: 게임, 서버, 아이템명, 가격, 수량, 한글 상태가 보인다. 비로그인 상세에 수정·삭제·상태 변경 폼이 없다

#### T07 존재하지 않는 상품

- 목적: 잘못된 id
- 사전 조건: 없는 id를 하나 고른다
- 실행: `GET /items/999999`와 숫자가 아닌 경로를 연다
- 예상 결과: "상품을 찾을 수 없습니다." SQL 오류 문구가 없다

#### T08 게임 필터와 이름 검색

- 목적: WHERE 조합
- 사전 조건: 서로 다른 게임의 상품, 이름이 겹치지 않는 상품
- 실행: 게임만 선택, 이름만 입력, 둘을 함께 적용, 없는 단어로 검색
- 예상 결과: 조건에 맞는 행만 보인다. 없는 단어는 "검색 결과가 없습니다."

#### T09 로그인 사용자의 상품 등록

- 목적: 정상 등록
- 사전 조건: A 로그인
- 실행: 유효한 서버, 이름, 가격, 수량, 설명으로 등록한다
- 예상 결과: 상세로 이동한다. 상태가 판매 중이다. `user_id`가 A다. 판매자는 A의 아이디로 보인다

#### T10 비로그인 등록

- 목적: 인증 없는 등록 차단
- 사전 조건: 쿠키 삭제
- 실행: `GET /items/create`와, 유효한 필드를 넣은 `POST /items`를 보낸다
- 예상 결과: 로그인 화면. `items` 행이 늘지 않는다

#### T11 필수값 누락

- 목적: 서버 검증
- 사전 조건: A 로그인
- 실행: 아이템명을 비우고 등록한다. 가격만 비운 경우, 서버를 비운 경우를 각각 한다
- 예상 결과: 각 경우 폼 오류. INSERT 없음

#### T12 음수와 0, 소수 가격

- 목적: 숫자 검증
- 사전 조건: A 로그인
- 실행: 가격에 `-1`, `0`, `1.5`, 수량에 `0`과 `-3`을 각각 제출한다
- 예상 결과: 모두 저장되지 않는다. CHECK까지 가기 전에 PHP가 거절한다

#### T13 본인 수정

- 목적: 작성자 수정
- 사전 조건: A의 판매 중 상품
- 실행: 이름과 가격을 바꿔 저장하고 DB를 확인한다
- 예상 결과: 상세에 새 값이 보인다. `user_id`와 `created_at`은 같다. `updated_at`은 달라진다

#### T14 타인 상품 수정

- 목적: 권한
- 사전 조건: A 로그인, B의 판매 중 상품 id
- 실행: 그 id의 수정 화면 GET과 수정 POST를 한다
- 예상 결과: 403. B의 행은 실행 전과 같다

#### T15 타인 상품 삭제

- 목적: 권한
- 사전 조건: A 로그인, B의 판매 중 상품 id
- 실행: 삭제 확인 GET과 삭제 POST를 한다
- 예상 결과: 403. 행이 남는다

#### T16 비로그인 수정과 삭제

- 목적: 인증
- 사전 조건: A의 판매 중 상품 id. 비로그인
- 실행: 수정 GET, 수정 POST, 삭제 POST를 한다
- 예상 결과: 로그인 화면. 행이 유지된다

#### T17 본인 삭제

- 목적: 확인 후 POST 삭제
- 사전 조건: A의 판매 중 상품
- 실행: 삭제 확인을 연 뒤 삭제한다. 같은 주소로 GET만 다시 연다
- 예상 결과: POST 후에는 목록 메시지와 함께 행이 사라진다. GET만 열었을 때는 행이 남는다

#### T18 허용된 상태 전환

- 목적: 판매 중 → 거래 진행 중 → 거래 완료, 그리고 진행 중 → 판매 중
- 사전 조건: A의 판매 중 상품 두 건
- 실행: 한 건은 진행 중을 거쳐 완료까지 변경한다. 다른 건은 진행 중으로 바꾼 뒤 판매 중으로 되돌린다
- 예상 결과: 각 단계 후 DB `status`가 그 값이다. 완료 상품 상세에는 상태 변경 폼이 없다

#### T19 허용되지 않는 상태 전환

- 목적: 전이 규칙
- 사전 조건: A의 판매 중 상품, A의 완료 상품
- 실행: 판매 중 상품에 `COMPLETED`를 POST한다. 완료 상품에 `ON_SALE`을 POST한다. `status`에 `DROP TABLE`을 POST한다
- 예상 결과: 400 메시지. 각 행의 상태가 그대로다

#### T20 타인 상태 변경

- 목적: 권한
- 사전 조건: A 로그인, B의 판매 중 상품
- 실행: `IN_PROGRESS`로 상태 POST
- 예상 결과: 403. B의 상태 유지

#### T21 SQL 인젝션 입력

- 목적: 바인딩
- 사전 조건: 목록에 상품이 여러 건
- 실행: 검색어에 `' OR '1'='1` 과 `%' OR 1=1 --` 를 넣는다. 가입 아이디에 `admin' --` 를 넣는다
- 예상 결과: 검색은 그 문장을 포함한 이름만 찾거나 0건이다. 전체 목록이 조건 없이 나오지 않는다. 아이디는 형식 오류다. 오류 화면에 SQL이 없다

#### T22 HTML과 스크립트 입력

- 목적: 출력 이스케이프
- 사전 조건: A 로그인
- 실행: 아이템명과 설명에 `<script>alert(1)</script>` 와 `<img src=x onerror=alert(1)>` 를 저장하고 목록, 상세, 수정 폼을 연다
- 예상 결과: 대화상자가 뜨지 않는다. 태그가 글자로 보인다. 수정 폼의 값 속성도 태그가 끊기지 않는다

#### T23 CSRF 누락

- 목적: 토큰 없는 변경 차단
- 사전 조건: A 로그인. 브라우저 개발 도구 또는 HTML을 저장한 요청으로 토큰 없는 POST를 만들 수 있다
- 실행: 토큰을 제거한 채 등록, 수정, 삭제, 상태 변경, 로그아웃을 각각 POST한다
- 예상 결과: 419. 상품 데이터와 로그인 세션이 유지된다. 정상 화면의 폼으로는 같은 동작이 성공한다

#### T24 완료·진행 중 상품의 수정과 삭제

- 목적: Q3 기본안의 상태 제한
- 사전 조건: A의 진행 중 상품, A의 완료 상품
- 실행: 각 상품에 수정 PUT과 삭제 DELETE를 한다
- 예상 결과: 403. 행이 유지된다. 진행 중 상품은 T18의 상태 변경만 된다

#### T25 비밀번호가 화면에 나오지 않음

- 목적: 해시와 평문 노출 방지
- 사전 조건: T01 계정
- 실행: 목록, 상세, 페이지 소스에서 비밀번호와 해시 접두사를 찾는다
- 예상 결과: 평문과 해시가 HTML에 없다

#### T27 내 판매 상품

- 목적: 자신의 행만 조회
- 사전 조건: A와 B가 각각 상품을 가짐. A 로그인
- 실행: `GET /my/items`를 연다. URL에 다른 회원 id를 붙여 본다
- 예상 결과: A의 상품만 보인다. B의 id 파라미터는 결과에 영향을 주지 않는다. 판매 중 행에만 수정·삭제가 있다

### 2.2 P1 시나리오

P1 기능을 구현한 뒤에만 실행한다. T27은 P0다.

#### T26 정렬

- 목적: 최신순과 가격순
- 사전 조건: 가격과 등록 시각이 다른 상품 3건 이상
- 실행: `sort=latest`, `sort=price_asc`, `sort=price_desc`, `sort=name;drop` 을 각각 연다
- 예상 결과: 세 허용 값은 해당 순서로 정렬된다. 잘못된 값은 최신순이다. SQL 오류가 없다

#### T28 페이지네이션

- 목적: 10건 단위
- 사전 조건: 같은 검색 조건의 상품 11건 이상. 시드로 만들거나 등록으로 만든다
- 실행: 1페이지와 2페이지, `page=0`, `page=abc`를 연다
- 예상 결과: 1페이지는 최대 10건. 2페이지에 나머지가 있다. 0과 문자는 1페이지와 같다. 행이 빠지거나 중복되지 않게 id 정렬 안정성을 확인한다

#### T29 좁은 화면

- 목적: 기본 반응형
- 사전 조건: P1 CSS 적용
- 실행: 브라우저 너비를 약 375px로 줄여 목록, 상세, 등록 폼을 본다
- 예상 결과: 주요 글자가 가로 스크롤 없이 읽힌다. 등록 버튼을 누를 수 있다
